# 最近 75 分钟监控升级验收

已部署到 [muluzzh00-cpu/pre-recommend-monitor](https://github.com/muluzzh00-cpu/pre-recommend-monitor)。本次升级继续使用原 monitor-state 状态分支，未初始化新的生产数据库。

## 本次行为

- 北京时间 Asia/Shanghai；每小时运行一次，实际运行时间向前取 75 分钟，边界均包含，未来发布时间不进入窗口。
- 先查库去重。相同 URL / 同校相同标题的已有公告只更新 last_seen_time，不重复进入详情。
- 精确发布时间保存为 publish_time；只有日期时为 null，今天首次发现则 potential_new_notice=true。相关性单独判断，无关公告不发邮件。
- 最新公告默认每个配置列表最多 40 条、最多 3 页，达到上限即停止翻页。只查可能的新公告详情，并用详情中的精确发布时间再次核对窗口。
- 全新数据库先建 baseline；仅明确在 2026-09-10 起发布、同时含 2027 和推免/直博、达到高相关性的通知可以合并提醒。其它历史公告只记录，不补发。
- 日期完全缺失时查一次详情；仍不明确则加入日报待核实，不发送普通新通知。
- 截止提醒继续检查所有已保存的有效截止事项；22 点日报按全天累计，保存当天各轮故障，网站恢复后不抹去历史故障。

旧版正式运行每轮 HTTP 请求 161 次（见 cloud-second.json）。本次统计包含 robots、列表、翻页及重试，因此数量会随网络波动变化，详情页请求单独列出。跳过数量按列表条目计数，同文跨栏目可多次跳过，所以可能大于数据库去重后的条数。普通新通知按事件统计，仍可能独立产生合法截止提醒或健康日报。

## 使用上的边界

标题不变而仅正文内部修改截止日期时，按本次“已知公告跳过详情”的要求，不会每小时重新检测该变化。旧截止提醒仍依照已保存的日期执行。官网长期不提供发布时间的公告需从日报链接人工核查。

75 分钟仅覆盖通常的短暂调度延迟；若 GitHub 延迟超过重叠时长，精确时间的公告仍可能落在空档，应适当增加 lookback_minutes。实际 schedule 的稳定性仍需观察；本次使用手动云端运行验证。监控结束时间仍为北京时间 2026-09-25 23:59:59。
